## Progress

### Hierarchical traversal implementation (Phase 2)
1. Implemented breadth-first hierarchical traversal with per-child `intersects()` testing
2. Added `shapely.prepare()` on source geometries for faster intersects()
3. **Discovered critical bug in `get_healpix_cell_geometry()`**: misread `healpy.boundaries()` return format. Treated 3D Cartesian `(x, y, z)` as `(theta, phi)` angular coordinates. Fixed by using correct conversion: `theta = arccos(z)`, `phi = arctan2(y, x)`.

### Root cause of empty results
After fixing the coordinate conversion, found that polar HEALPix cells (e.g., cell 11 at NSIDE=1) wrap around the south/north pole in ways that cannot be represented as simple lon/lat polygons. The cell spans from 315° through 0° to 270° through the pole. `shapely.Polygon` collapses this to a degenerate shape covering 0°–270° latitude, missing the source polygon at lon=324°, lat=-41°.

This is a fundamental limitation: any polygon-based cell geometry approach fails at the poles. The STRtree path in `healpix_to_geodataframe()` handles this via `antimeridian.fix_polygon` and multi-part representations.

### Decision: abandon hierarchical traversal
Rather than fight polar cell geometry with spherical-geometry libraries, decided to:
1. Keep Phase 1 optimization: `shapely.prepare()` on grid and source geometries
2. Remove the broken `_builtin_hierarchical_healpix()` function
3. Directly use STRtree query in `process_partition()` (no hierarchical step)
4. Retain dense sampling fallback

### Fuzzy mode missing cells bug
User reported fuzzy mode at n=32 missing cells for their MESSENGER MASCS data.
Root cause found: `_is_valid_latitude()` in `process_partition()` used `lon_convention`-specific bounds (-180..180 or 0..360) to validate input geometry coordinates. User's data has geometries in 0-360 convention. When user passed `--lon-convention minus_plus180`, ALL geometry coordinates with lon > 180 were rejected → 49999/50000 geometries dropped → zero output cells.
Fix: changed `_is_valid_latitude()` to use ±360 for lon bounds regardless of `lon_convention` (lat stays -90..90). The `lon_convention` only controls HEALPix grid construction, not input data validation.

### Verification (after fix)
- All 196 tests pass
- 5k sample: n=4 → 99.5% of sphere, n=32 → 33.0% (4092 cells), n=64 → 11.5%
- STRtree + dense-sampling merge (from earlier fix) catches corner/edge intersections
- Both strict and fuzzy modes work correctly with both lon conventions
